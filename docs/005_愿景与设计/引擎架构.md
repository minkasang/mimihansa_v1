# 引擎架构：通用NPC行为框架

> 这是引擎层的核心设计。所有领域系统（吃饭/恋爱/工作/建房/打架/传播信息…）都通过这个统一框架运转。
> ⚠️ 设计规格书 —— 定义了引擎的输入/处理/输出和数据流。

---

## 一、引擎的根本逻辑：一个通用的决策循环

```
每个NPC每Tick执行同一个循环（不区分"他在做什么事情"——引擎不关心）：

  [输入] NPC当前的状态快照 + 感知到的世界信息
    ↓
  [条件筛查] 遍历所有欲望库条目，检查触发条件
    ↓
  [效用打分] 对符合条件的欲望计算效用分
    ↓
  [选择] 选分最高的 → 如果比当前目标高分 → 打断当前目标
    ↓
  [规划] GOAP：把目标拆成指令序列
    ↓
  [执行] 一条一条执行指令 → 每执行一步改变NPC状态
    ↓
  [输出] NPC新状态、产生的新事件、世界被改变的结果
```

**引擎不区分业务。** 它不知道"想吃饭"和"想恋爱"的区别——它们都是"一条欲望+一个目标+一堆指令+一些效果"。引擎只是这个循环的执行者。

## 二、引擎的模块构成

```
Engine
├── [数据加载器]        静态数据一次性读入
│   ├── Desires_Library    → 所有可能的欲望
│   ├── Actions_Library    → 所有可能的动作
│   ├── Quests_Library     → 复杂的多阶段任务
│   ├── Interrupts_Library → 可打断当前目标的事件
│   ├── Dialogues_Library  → 对话模板
│   └── Brains_Library     → 性格-动作打分映射
│
├── [运行时管理者]
│   ├── NPCManager          → 管理所有NPC的实例
│   ├── WorldState          → 当前世界的快照（时间/天气/地图/Tick计数）
│   └── (未来) MapManager   → 地图数据
│
├── [每Tick循环]
│   ├── 环境感知           → 更新每个NPC的视觉/听觉/嗅觉
│   ├── 生理状态推进       → 饥饿+1、疲劳+1、经期日+1……
│   ├── 欲望评估器         → 遍历欲望库 → 输出可能的欲望列表
│   ├── 效用打分器         → 为每个欲望计算加权分数
│   ├── 目标选择           → 选得分最高的 → 创建GOAP目标
│   ├── GOAP规划器         → 目标 → 拆解为指令序列
│   ├── ModuleRegistry     → 执行实际指令
│   └── 效果结算           → 改变NPC参数 → 产生事件 → 更新世界
│
├── [周期钩子]
│   ├── 事件检测器         → 出生/死亡/学龄/就业/……（每Tick检查一次）
│   ├── 关系管理器         → 好感度增减、社交网络更新
│   ├── 信息传播器         → 口口相传、信息交换
│   └── 市场结算器         → 价格更新、生产/交易/雇佣结算
│
└── [外部接口]
    ├── getSnapshot()       → 返回世界快照给UI层
    └── 未来可能接入LLM     → 在特定场景下接管决策
```

## 三、引擎不了解业务——它只了解三样东西

### 3.1 参数

```
引擎只认这些数据结构（来自参数总表）：
  NPC.生理状态.饥饿度 = 数字
  NPC.性格.色欲 = 1-10
  NPC.社会关系.好感度 = -100~+100
  World.时间.当前小时 = 0~23
  Perception.nearbyNPCs = [...]
  
引擎不关心这些参数"代表什么意义"，它只做数学运算。
```

### 3.2 条件

```
每条欲望/动作都有一个条件字段：
  条件格式：[属性, 操作符, 值]
  例如：
    {"NPC.生理状态.饥饿": [">", 7]}   → 引擎执行：if (NPC.生理状态.饥饿 > 7) { 触发 }
    {"NPC.性格.色欲": [">=", 5]}     → if (NPC.性格.色欲 >= 5) { 触发 }
    {"感知.附近有NPC": ["==", true]}  → if (感知.nearbyNPCs.length > 0) { 触发 }
    {"且": [条件1, 条件2]}             → if (条件1 && 条件2) { 触发 }
    {"或": [条件1, 条件2]}             → if (条件1 || 条件2) { 触发 }

ConditionEvaluator（已有）只需要支持这几种条件格式。
任何欲望用这个格式写 → 引擎都能评估。
```

### 3.3 效果

```
每条指令执行后产生效果：
  效果格式：{"参数名": 变化值}
  例如：
    {"饥饿": -3}          → 引擎：NPC.生理状态.饥饿度 -= 3
    {"开心": 2}           → 引擎：NPC.生理状态.开心值 += 2
    {"物品栏": "+苹果"}    → 引擎：NPC.物品栏.add("苹果")
    {"金钱": -5}           → 引擎：NPC.金钱 -= 5

引擎不关心"为什么饥饿会减"，只关心参数改了。
同样由效果结算器统一处理，不管是什么类型的动作。
```

## 四、为什么这个框架很强大

### 新增一个玩法（比如"遛狗"）：只需改3个JSON

```
步骤1：Desires_Library.json 加一条
{
  "欲望id": "want_walk_dog",
  "名称": "想遛狗",
  "触发条件": {"且": [
    {"NPC.物品栏.已有标签": ["包含", "狗"]},
    {"NPC.生理状态.疲劳": ["<", 5]},
    {"World.天气.下雨": ["==", false]}
  ]},
  "优先级": 3,
  "生成目标": {"目标类型": "休闲", "动作id": "action_遛狗"}
}

步骤2：Actions_Library.json 加一条
{
  "动作id": "action_遛狗",
  "名称": "遛狗",
  "指令序列": [
    {"module": "move_in_area", "params": {"center": "$家坐标", "radius": 10}},
    {"module": "wait", "params": {"duration": 5000}}
  ],
  "效果": {"开心": 2, "疲劳": 1}
}

步骤3：Dialogues_Library.json（可选）加一条对话模板
{
  "id": "walk_dog_chat",
  "对话列表": ["走，狗狗出去逛逛！", "今天天气真好，带狗出去溜一圈~"]
}

← 引擎不需要任何代码变更 ← 新的"遛狗"玩法已激活
```

### 引擎只有一套循环，不区分"生老病死"还是"吃饭恋爱"

所有系统（出生/死亡/教育/恋爱/工作/市场/信息传播…）都是
**"一条欲望 + 一个条件 + 一个指令序列 + 一个效果"**。

引擎不需要知道"这是在恋爱"还是"这是在吃饭"。
它只是：
1. 评估所有欲望
2. 选出当前最好的
3. 拆成指令去执行

## 五、引擎的"管道"：数据从哪儿来、到哪儿去

```
[数据来源]
  ├── NPC个人信息.json   → NPC参数表的所有字段
  ├── World snapshot      → 时间/天气/地图
  ├── Perception         → 每Tick更新的视觉/听觉/嗅觉
  └── Libraries          → 欲望库/动作库/对话库/任务库/中断库/大脑库

[数据流]
  NPC参数 + 世界快照 + 感知 → DesireEvaluator
     ↓
  候选欲望列表 → ScoreCalculator / GOAPPlanner
     ↓
  生成目标 → ModuleRegistry → 执行指令
     ↓
  效果输出 → 更新NPC参数 + 产生事件 + 更新世界

[数据出去]
  ├── NPC个人信息.json (写)  → 持久化
  ├── 朋友.json (写)          → 关系持久化
  ├── 记忆/ (写)              → 事件持久化
  ├── UI snapshot (读)        → getSnapshot() 给UI层
  └── 世界事件日志 (写)       → 历史记录
```

## 六、引擎的性能设计

### 6.1 每个NPC的计算很轻

```
每一步都是数学运算 → 没有网络请求、没有数据库查询、没有LLM推理
一个NPC每Tick的计算量：
  条件处理 ≈ <0.01ms (if-else)
  打分     ≈ <0.005ms (乘法)
  规划     ≈ <0.1ms (GOAP: 迭代+排序)
  执行指令 ≈ <1ms (路径/A*/对话)
  总计     ≈ <2ms per NPC per Tick

1000个NPC → 2s/tick → 必须降频
方案：欲望计算20% NPC/tick → 每个NPC每5Tick才重新计算一次欲望
大部分NPC在"空闲/执行长动作"状态，跳过打分
```

### 6.2 降频策略（已在Tick主循环中定义）

| 操作 | 频率 | 说明 |
|:-----|:----|:-----|
| 生理状态 | 每Tick | 极轻量加减法 |
| 欲望计算 | 每5~10 Tick | 降频不影响体验 |
| 信息传播 | 随机配对+NPC/tick | 抽样 |
| 市场结算 | 每天一次 | 价格不需要每秒变 |

## 九、新增引擎机制（v1.1 新增）

> ⚠️ 以下机制是 Kimi_核心缺失环节清单 中识别出的引擎层缺失，已在代码中初步实现。

### 9.1 子目标链机制（Sub-Goal Chain）

**问题**：当前引擎是单层决策（欲望→目标→动作→结束），NPC遇到"前提条件不满足"时直接卡死。

**解决方案**：GOAP规划器扩展，支持目标→子目标的递归拆解。

```
现实链路：
  饿了 → 想吃 → 没食物？ → 子目标：获取食物
    → 去哪获取？
      → 方案A：去采摘（需要知道野果位置）
      → 方案B：去购买（需要有钱+知道商店位置）
    → 选择方案A
      → 子目标：去森林 → 移动到森林
      → 子目标：采摘 → 执行采摘动作
      → 子目标：吃 → 执行吃动作

当前实现：
  want_eat 触发 → action_eat（背包有食物直接吃）
  want_forage 触发 → action_forage（背包没食物时采摘）
  → 两者通过条件互斥实现"子目标链"效果
```

**当前状态**：已通过欲望条件互斥实现简单子目标链（want_eat饥饿>5触发，want_forage饥饿>5且背包空触发）。完整递归子目标链待阶段一实现。

**对应代码**：`Desires_Library.json` 中 want_eat / want_forage / want_drink 的条件设计

---

### 9.2 持续性意图栈（Persistent Intent Stack）

**问题**：当前引擎每5-10 Tick重新计算所有欲望，"追求小美"和"晒太阳"平等竞争。

**解决方案**：NPC维护一个长期意图列表，高优先级的长期意图压制短期欲望。

```typescript
interface PersistentIntent {
  id: string;
  类型: "追求" | "学习" | "攒钱" | "储备" | "建造" | "复仇" | "探索";
  目标: any;
  优先级: number;          // 1-10
  进度: number;            // 0-100
  子目标: string[];
  创建时间: number;
  截止时间?: number;
}
```

**当前状态**：interface已定义（`types/npcTypes.ts`），运行时逻辑待阶段二实现。

**对应代码**：`types/npcTypes.ts` → PersistentIntent

---

### 9.3 事件系统（EventBus）

**问题**：跨系统触发链（A发生→触发B→触发C）没有统一机制，散落在各处。

**解决方案**：全局事件总线，统一"A发生→触发B"的机制。

```typescript
interface GameEvent {
  类型: string;        // "NPC死亡" | "建筑完工" | "好感度变化" | "分娩" | ...
  来源: string;        // 触发者ID
  目标?: string;       // 目标ID
  数据: Record<string, any>;
  时间戳: number;
}

class EventBus {
  on(eventType: string, listener: (event: GameEvent) => void): void;
  emit(event: GameEvent): void;
  off(eventType: string, listener: Function): void;
}
```

**当前状态**：已实现（`engine/EventBus.ts`），全局实例 `globalEventBus` 可用。

**对应代码**：`engine/EventBus.ts`

---

### 9.4 时间系统（TimeSystem）

**问题**：不同文档对时间的描述单位不统一（秒/小时/天/月/年混用），没有统一转换层。

**解决方案**：统一时间配置 + 转换函数 + 季节判定。

```
时间配置：
  1 Tick = 1 秒（游戏时间）
  1 天 = 86400 Tick = 24 小时
  1 月 = 30 天
  1 季节 = 3 月
  1 年 = 4 季节 = 12 月

白天判定：6:00 - 18:00
季节判定：春1-3月 / 夏4-6月 / 秋7-9月 / 冬10-12月
```

**当前状态**：已实现（`engine/TimeSystem.ts`），包含：
- `TIME_CONFIG` 常量
- `ticksToDays()`, `ticksToHours()`, `daysToTicks()` 等转换函数
- `getSeason()`, `isDaytime()` 判定函数
- `tickToWorldTime()` Tick数→WorldTime结构转换
- `createInitialTime()` 初始时间（第1年3月1日8:00，春季）

**对应代码**：`engine/TimeSystem.ts`

### 9.5 感知→欲望映射（Perception-Action Loop）

**问题**：当前感知系统是"被动的"——每Tick更新感知结果，但不直接驱动行为。

**解决方案**：感知触发器（PerceptionTrigger），感知结果直接生成欲望。

```typescript
interface PerceptionTrigger {
  感知类型: "视觉" | "听觉" | "嗅觉" | "触觉";
  过滤条件: (感知结果, npc) => boolean;
  生成欲望: (npc, 感知结果) => { id: string; target?: any } | null;
  优先级: number;
  冷却时间: number;
}
```

**当前状态**：interface已定义（`types/worldTypes.ts`），运行时逻辑待阶段二实现。

**对应代码**：`types/worldTypes.ts` → PerceptionTrigger

### 9.6 Agent抽象基类

**问题**：当前引擎硬绑NPC数据结构，动物无法接入。

**解决方案**：定义Agent抽象基类，NPC和Animal分别实现。

```typescript
interface Agent {
  id: string;
  位置: [number, number];
  当前动作: string;
  getDesires(): Desire[];
  evaluateDesires(): Desire;
  planActions(desire: Desire): Action[];
  executeAction(action: Action): void;
}
```

**当前状态**：设计定义完成，代码实现待阶段二。

**对应代码**：`types/npcTypes.ts` → Animal interface, `types/worldTypes.ts` → Animal interface

### 9.7 条件评估器扩展（ConditionEvaluator v1.1）

**问题**：原ConditionEvaluator只支持6个操作符，文档中需要12+种。

**新增操作符**：

| 操作符 | 用途 | 示例 |
|:-------|:-----|:-----|
| `"有标签"` | 检查NPC标签 | `{ "标签": ["有标签", "婴儿"] }` |
| `"无标签"` | 检查NPC没有标签 | `{ "标签": ["无标签", "夫妻"] }` |
| `"物品栏有"` | 检查背包有某物品 | `{ "物品栏": ["物品栏有", "石刀"] }` |
| `"物品栏有标签"` | 检查背包有某标签物品 | `{ "物品栏": ["物品栏有标签", "武器"] }` |
| `"物品栏无标签"` | 检查背包没有某标签物品 | `{ "物品栏": ["物品栏无标签", "工具"] }` |
| `"季节是"` | 检查当前季节（数组格式） | `{ "World.时间": ["季节是", "秋"] }` |
| `"季节是"` | 检查当前季节（特殊key格式） | `{ "季节是": "秋" }` |
| `"是白天"` | 检查是否白天（数组格式） | `{ "World.时间": ["是白天"] }` |
| `"是白天"` | 检查是否白天（特殊key格式） | `{ "是白天": true }` |
| `"是黑夜"` | 检查是否黑夜（特殊key格式） | `{ "是黑夜": true }` |
| `"知识库有"` | 检查知识库 | `{ "知识库": ["知识库有", "地点"] }` |
| `"附近有"` | 检查感知范围（特殊key格式） | `{ "附近有": "火堆" }` |
| `"是亲属"` | 检查亲属关系 | `{ "社会关系": ["是亲属", "$目标ID"] }` |
| `"随机<"` | 随机概率 | `{ "概率": ["随机<", 0.05] }` |
| `"为空"` | null/undefined/空数组判断 | `{ "家坐标": ["为空"] }` |
| `"不为空"` | 非空判断 | `{ "家坐标": ["不为空"] }` |

> ⚠️ 条件格式有两种写法：
> 1. **数组格式**：`{ "字段路径": ["操作符", 值] }` — 通用格式，字段路径支持点号嵌套
> 2. **特殊key格式**：`{ "是白天": true }`, `{ "附近有": "火堆" }` — 简写格式，不需要字段路径
> 两种格式可以混用在"且"/"或"逻辑组合中

**当前状态**：已实现（`engine/ConditionEvaluator.ts` v1.1）

**对应代码**：`engine/ConditionEvaluator.ts`
