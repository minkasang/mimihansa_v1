## 一、五感：NPC怎么感知世界

### 1.1 视觉（眼睛）

```
每个NPC有一个视野属性：
  视野半径 = 基础20格
  增加因素：
    站在高处（山地）→ +10格
    白天/晴天      → +5格
    夜晚/大雾      → -10格
    老年人         → -5格

感知内容（在视野半径内可感知的东西）：
  - 地形、建筑、物品（所有可见物）
  - 其他人（能看到是男是女、大概特征、在干什么）
  - 事件（打架、生火、建造——产生视觉事件）
```

### 1.2 听觉（耳朵）

```
听觉半径 = 基础30格
  说话声音大小影响传播距离：
    小声说话（悄悄话）→ 5格以内可听到
    正常说话         → 15格以内可听到
    大声喊叫         → 30格以内可听到
    建筑/墙壁隔音    → 有墙挡着-10格

感知内容：
  - 别人的说话内容（在听觉半径内→听到"
  - 环境声音（打架声、生火声、砍树声，声音大→传播远）
  - 哭声（婴儿的哭声穿透力强，+10格）
```

### 1.3 嗅觉（鼻子）

```
嗅觉半径 = 基础10格
  风的方向影响：
    顺风 → ×2（上风处闻到下风处）
    逆风 → ×0

感知内容：
  - 食物（有人在烤肉的香味，吸引其他人过来）
  - 火灾（烧焦味——可能触发避险）
  - 腐烂（尸体的臭味——注意，这里有东西死了）
```

### 1.4 触觉（默认全感知）

```
触觉不需要范围——身体接触到的自动感知。
感知内容：
  - 被人碰到 → 产生触觉事件
  - 冷/热 → 天气系统的暴露度
```

### 1.5 五种感官的数据结构

```typescript
interface NPCSenses {
  视野半径: number;     // 由视力+环境确定
  听觉半径: number;     // 固定30，受发言音量影响
  嗅觉半径: number;     // 固定10
  触觉: boolean;        // 总是true
  
  当前看到的内容: PerceptionResult[];  // 每Tick更新
  当前听到的内容: PerceptionResult[];
  当前闻到的内容: PerceptionResult[];
}

interface PerceptionResult {
  类型: '视觉' | '听觉' | '嗅觉' | '触觉';
  目标: string;        // 是什么（建筑ID/NPC ID/事件名称）
  距离: number;
  详情: object;        // 具体信息（说的话内容、味道类型等）
}
```

## 二、口口相传：信息传播

### 2.1 聊天是怎么发生的

```
两个NPC在各自的听觉半径内 → 可能触发聊天

聊天的条件：
  1. 双方都不是[战斗]状态
  2. 双方没有仇恨关系
  3. 至少一方有[社交]的意愿
  4. 双方距离 < 听觉半径

聊天频率：
  朋友/熟人 → 每隔几天会自然聊一次
  陌生人   → 如果没事，可能也会路过打招呼
```

### 2.2 聊什么（信息交换）

```
聊天时，双方从自己的知识库中各取一条信息分享：

分享优先级：
  1. 最近发生的大事（如"昨天我打到了一只鹿" "某家生了孩子"）
  2. 对方不知道但自己知道的（信息差）
  3. 闲话/八卦

A告诉B → B的知识库新增一条：
  来源：A告诉我的
  内容：A说的内容
  可信度：取决于B对A的信任（如果A是个骗子，B可能不信→待未来扩展）

B也能告诉C → C再告诉D → 信息扩散
扩散时长：一个消息从孤立的A传到全村（100人）：约2~3天
```

### 2.3 谣言与信息失真（可选，先预留）

```
当信息传递超过3手：
  传递每多一手 → 信息失真概率 +20%

失真效果：
  原始消息："张三昨天打到了一只鹿"
  5手之后："听说张三家跑出来一群鹿"
  10手之后："山里的鹿群要来踩我们的田了"

这个机制让"道听途说"的文化功能真实再现
```

### 2.4 公示栏——另一种传播方式

```
公示栏读写双向（职业与市场系统 §4.1）

与口口相传的区别：
  公示栏 → 一次写入，多人读取（可持久，但需要主动去看）
  口口相传 → 点到点传播（依赖社交，可能失真）

两者互补：
  公示栏存在 → 陌生人也可以获取信息（不需要认识任何人）
  公示栏不存在→ 信息只能走社交网络
```

## 三、信息传播的边界——NPC不能知道什么

### 3.1 已知 vs 未知的判定

```
NPC知道某条信息的条件（满足一个就行）：
  ✅ 亲眼看到了
  ✅ 亲耳听到了
  ✅ 别人告诉他的（记忆库里有记录）
  ✅ 公示栏上看到的

NPC不知道的条件（所有条件都不满足）：
  ❌ 不在视觉/听觉范围 → 不可能知道
  ❌ 没有在公示栏看过 → 不可能知道
  ❌ 没人告诉他 → 不可能知道
```

### 3.2 常识：当大部分人知道了

```
"常识"的判定：
  在某个地理范围内（同村），有已知信息的NPC人数 >= 总人数的80%
  → 该信息标记为"常识"

常识的效果：
  - 新NPC来到村子 → 可能很快听到"常识"（因为80%的人都知道，聊着聊着就会说）
  - NPC可以"常识"为依据做决策（不需要被动去收集信息）
```

### 3.3 个人隐私 vs 公开信息

```
公开信息（对话中自动分享）：
  - 天气
  - 村里发生的大事
  - 自己见到的东西

个人隐私（不会主动分享）：
  - 自己的内心状态（难过、焦虑）
  - 对他人的负面评价
  - 自己做了坏事
  - 自己有多少钱

是否分享隐私取决于性格：
  社交属性_自我坦露 ≥ 7 → 可能主动分享心事
  人际关系_猜疑程度 ≥ 7 → 什么都不说
  情绪基调_积极倾向 ≤ 3 → 心情不好时什么都不会透露
```

## 六、感知触发器（v1.1 新增）

> ⚠️ 原感知系统是"被动的"——每Tick更新感知结果，但不直接驱动行为。
> 感知触发器让感知结果直接生成欲望，实现"感知→行为"的闭环。

### 6.1 感知触发器定义

```typescript
interface PerceptionTrigger {
  感知类型: "视觉" | "听觉" | "嗅觉" | "触觉";
  过滤条件: (感知结果: PerceptionResult, npc: NPC) => boolean;
  生成欲望: (npc: NPC, 感知结果: PerceptionResult) => { id: string; target?: any } | null;
  优先级: number;        // 1-10，高优先级压制低优先级短期欲望
  冷却时间: number;      // Tick数，防止重复触发
}
```

### 6.2 已设计的感知触发器

| 触发器 | 感知类型 | 触发条件 | 生成欲望 | 优先级 | 冷却 |
|:-------|:---------|:---------|:---------|:------:|:----:|
| 婴儿哭声 | 听觉 | 听到哭声+同理心>5 | want_care_for_child | 8 | 300 |
| 食物香味 | 嗅觉 | 闻到食物香味+饥饿>5 | want_eat | 7 | 600 |
| 火堆 | 视觉 | 看到火堆+有生肉 | want_cook | 5 | 300 |
| 陌生人 | 视觉 | 看到陌生人+社交欲>5 | want_socialize | 4 | 600 |
| 危险 | 视觉/听觉 | 看到战斗/听到喊叫 | want_flee | 9 | 0 |
| 建造中 | 视觉 | 看到别人在建房子+友善>5 | want_help_build | 3 | 1200 |

### 6.3 与ConditionEvaluator的衔接

感知触发器生成的欲望，会进入DesireEvaluator的正常评估流程。
触发器注入的欲望带有 `_worldTime` 和 `_perception` 扩展上下文，
使ConditionEvaluator能使用"季节是""附近有""是白天"等新操作符。

对应代码：`types/worldTypes.ts` → PerceptionTrigger

## 七、辨识符机制：NPC怎么"记住人脸"（v1.2 新增）

> ⚠️ 真实世界里你靠人脸记住一个人。程序里我们不做面部识别算法——用辨识符模拟。

### 7.1 核心逻辑

```
NPC "张文博" 第一次看到 "齐玲玲"（引擎知道她是 system_id = "npc_qilinlin"）：

感知系统内部（不写入NPC数据）：
  1. 检测到实体 → 拿到 system_id = "npc_qilinlin"
  2. 查张文博专属的人脸映射表（引擎内存，运行时，不持久化）：
     - 这个 system_id 之前见过吗？ → 没
  3. 生成一个新辨识符 = "r_001"（张文博自己世界里的编号，递增生成）
  4. 记录映射：r_001 → npc_qilinlin（存在内存，下次见到能对上）
  5. 在张文博.知识库里创建一条人物条目

第三次见到齐玲玲：
  1. 检测到 system_id = "npc_qilinlin"
  2. 查映射表 → 已经绑定了 r_001
  3. 更新张文博.知识库里 r_001 那条 → 追加见面记录
```

### 7.2 引擎内部映射表

```typescript
// 每个NPC在引擎内存里维护一张"人脸→辨识符"映射表
// 这个表不写入NPC的数据文件，只在运行时存在

interface FaceMapping {
  system_id: string;      // 引擎内部用，匹配实体
  npc_辨识符: string;     // NPC自己世界里的"身份证号"，如 "r_001"
}

// 全局映射表（引擎内存）
const npcFaceMaps: Record<string, FaceMapping[]> = {
  "npc_yunfei": [
    { system_id: "npc_qilinlin", npc_辨识符: "r_001" },
    { system_id: "npc_wangwu",   npc_辨识符: "r_002" },
    { system_id: "npc_liukun",   npc_辨识符: "r_003" }
  ],
  "npc_wangwu": [
    { system_id: "npc_qilinlin", npc_辨识符: "r_001" },
    { system_id: "npc_yunfei",   npc_辨识符: "r_002" }
  ]
};
```

**重要**：`system_id` 永远不会进入NPC的数据文件。映射表只存在于引擎运行时内存中。
辨识符才是NPC世界里唯一引用另一个人的方式。

### 7.3 辨识符在知识库中的形态

```typescript
// 张文博.知识库 中关于齐玲玲的条目
{
  id: "kb_0056",
  类型: "人物",
  辨识符: "r_001",                    // ← 张文博给这个人起的"内部代号"
  称呼: "好看的陌生人",                // 第一次见自动生成，随着了解渐深而更新
  我眼中的TA: {
    外貌: { 颜值: 8, 身高: "中等", 体型: "偏瘦" },
    标签: ["陌生", "好看", "经常去药铺"]
  },
  见面记录: [
    { 次数: 1, 时间: "第3天 上午", 地点: "药铺", TA在干什么: "买东西" },
    { 次数: 2, 时间: "第5天 下午", 地点: "集市", TA在干什么: "卖菜" }
  ],
  我知道的事: [
    { 内容: "她好像经常去药铺", 来源: "亲眼", 可信度: 0.8 },
    { 内容: "黄志远说她叫齐玲玲", 来源: "亲耳", 可信度: 0.5 }
  ]
}
```

### 7.4 称呼的动态进化

```
第一次见     → 最突出的外貌特征 + "陌生人"
              例："好看的陌生人"、"高个子陌生人"

见面超过3次  → "那个" + 特征 + "的"
              例："那个好看的"、"那个经常去药铺的"

知道了名字   → 可信度 > 0.7 → 称呼升级为真名
              例："齐玲玲"
```

称呼升级是NPC自己的知识库更新，不影响其他NPC对同一个人的称呼。

### 7.5 同一个齐玲玲，在不同NPC眼里

| | 张文博 对齐玲玲 | 黄志远 对齐玲玲 | 齐玲玲 自己 |
|:--|:-----------|:-----------|:----------|
| 辨识符 | `r_001` | `r_005` | — |
| 称呼 | "好看的陌生人" | "齐玲玲" | "我" |
| 标签 | [陌生, 好看] | [朋友, 善良, 铁匠女儿] | — |
| 颜值评价 | 8 | 5（黄志远不好这口） | — |
| 见面次数 | 2 | 50 | — |

### 7.6 信息壁垒的落地

辨识符机制是 §8.6 信息壁垒在感知层的具体实现：

- system_id 只存在于引擎内存映射表中 → NPC 绝不知道
- NPC 的所有计算（欲望、对话、社交）只读自己知识库里的辨识符
- 辨识符只是一串无意义的编号 → NPC 无法通过它反推到任何系统数据
- 两个 NPC 对同一个人的辨识符不同 → 信息天然隔离

### 7.7 与现有 IO 注册表的衔接

辨识符的生成和映射维护属于**步骤2（环境感知）**的子步骤：

```
步骤2.1 感知扫描（已有）
步骤2.2 辨识符匹配与生成（v1.2 新增）
  - 对每个感知到的实体 → 查映射表
  - 新实体 → 生成辨识符 + 创建知识库人物条目
  - 旧实体 → 匹配已有辨识符 + 更新知识库
步骤2.3 写入知识库（已有）
```
