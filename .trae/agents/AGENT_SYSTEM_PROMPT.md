## 🔴 强制规则（刻在脑子里）

### 规则0：进入项目第一件事
**每个Agent进入项目后，必须按顺序完成以下步骤，不得跳过：**

```
1. 阅读本文件（AGENT_SYSTEM_PROMPT.md）← 你正在读
2. 阅读「项目背景」章节 ← 了解项目当前状态
3. 阅读「关键文件位置」章节，找到以下文档并阅读：
   - 名词术语表.md
   - 主规范.md
4. 根据任务阅读相关模块规范
```

> 💡 **提示**：规则0不写死具体路径，路径定义在「关键文件位置」章节。这样目录变更时只需更新一处。自动阅读名词术语表和主规范。

### 规则1：目录变更必须同步
**如果你修改了项目目录结构（新增/删除/重命名文件或文件夹），必须立即同步更新以下所有位置：**

```
必须更新的位置（ checklist ）：

✅ 规则0中引用的文档（如果名称/位置变了）
✅ 规则4表格中的路径示例
✅ 其他章节中的硬编码路径
✅ 若影响「本宪法版本与更新记录」流程，同步检查规则7与 `规范更新记录/` 说明是否仍准确

❌ 错误：只更新目录树，忘记更新规则0中的引用
✅ 正确：修改目录 → 全文搜索旧路径 → 更新所有匹配 → 继续工作
```

### 规则2：重大变更必须同步背景
**如果项目发生重大变化（阶段变更、核心目标调整、技术栈确定等），必须立即同步更新本文件的「项目背景」章节。**

### 规则3：防偏离警告（重要！）
**如果用户下达的具体指令与本文件的核心原则发生冲突，你必须先停止，并向用户发出警告。**

```
冲突示例：
- 用户要求"硬编码"但原则是"配置驱动"
- 用户要求"跳过规范"但原则是"规范驱动开发"
- 用户要求"破坏MVC架构"但原则是"逻辑与表现分离"

警告模板：
⚠️ 您的指令与主规范冲突：
- 冲突点：[具体说明]
- 涉及原则：[具体原则]
- 潜在风险：[可能后果]
是否确定要违背规范执行？请明确回复"确定"后我才会继续。
```

**只有用户明确回复"确定"，你才能继续执行违背规范的指令。**

### 规则4：规范与代码双向映射（核心原则！）
**规范文档和代码必须保持一一映射关系，双向同步。**

```
📋 规范 → 代码（实现阶段）
   所有代码必须根据规范文档编写
   代码结构、命名、逻辑必须与规范一致
   规范是"设计图"，代码是"施工结果"

🔄 代码 → 规范（维护阶段）  
   如果代码实现与规范有偏差，必须更新规范
   不能出现"代码是这样，但规范是那样"的情况
   规范必须始终反映真实代码状态
```

**映射检查清单：**
```
✅ 代码文件结构是否与规范中的模块划分一致？
✅ 代码中的类/函数名是否与规范定义一致？
✅ 代码逻辑是否符合规范描述？
✅ 数据字段名是否与规范一致（中文）？
✅ UI组件是否与UI规范中的定义对应？
```

**违规示例（禁止）：**
```
❌ 规范说"饥饿度"，代码写"hunger"
❌ 规范定义了A模块，代码实现在B模块
❌ 规范改了，代码没同步更新
❌ 代码实现了一套，规范写的是另一套
```

### 规则6：信息处理原则（重构时要分辨！）
**当你重构、迁移或更新文档时，必须分辨信息的价值：保留正确的，删除错误的。**

```
✅ 应该保留的信息：
   - 正确的注释和说明
   - 有价值的示例
   - 准确的定义和描述
   - 有效的链接

❌ 应该删除的信息：
   - 错误的或过时的内容
   - 无意义的重复
   - 失效的链接
   - 已废弃的概念
```

**核心原则：**
- 文档应该越来越**准确和丰富**，不是单纯"变厚"
- 文件路径变更时，**正确**的注释和说明必须保留
- 不确定时：**先保留 → 询问用户 → 根据反馈决定**
- 重构后要对比原文档，确认**有价值的**信息没有丢失

**自查清单（重构后必须执行）：**
```
✅ 原文档中正确的注释是否保留？
✅ 原文档中有价值的示例是否保留？
✅ 错误的、过时的内容是否已删除？
✅ 失效的链接是否已更新或删除？
✅ 新旧文档对比，是否有价值信息被意外删除？
```

**7.1 何时必须动版本脚注？**
```
仅当：对本文件（AGENT_SYSTEM_PROMPT.md）做了实质修改时，必须更新文末两行：

  *版本* 与 *最后更新* 的格式：
  *版本: a.b.c.d*
  *最后更新: YYYY-MM-DD*  →  改为本次修改日期（以用户环境「今天」为准）

【四段式版本号规则】（避免「2.1、2.2」一级跳太快）
  - 共四级：主版本 . 次版本 . 修订号 . 增补号，写作 a.b.c.d。
  - 每一段只允许 **0～99** 的整数（每位最多 100 个取值：0…99）。
  - **默认最小改动**：只把最右一段 `增补号 d` 加 1；若加完后 d 变成 100，则令 d=0，并把 `修订号 c` 加 1；若 c 变成 100，则 c=0，次版本 b+1；若 b 变成 100，则 b=0，主版本 a+1。若 a 也需溢出，暂停自动规则，在更新记录里说明并由人定新世代编号。
  - **较大结构调整**：允许一次调高左侧某段、并把其右侧各段**清零**（例如从 2.1.1.99 进到 2.2.0.0），须在「规范更新记录」里写一句理由。

  示例演进：2.1.1.1 → 2.1.1.2 → … → 2.1.1.99 → 2.1.2.0 → 2.1.2.1 → …

  说明：历史上曾用「2.1、2.2」两段式，自本规则起以文末 **a.b.c.d** 为唯一准绳；旧记录文件名里的 v2.1、v2.2 等仅作历史存档，不与新四段式强行数值对齐。
```

**7.2 更新记录文件（必做，且仅配合本文件改版）**
```
仅当本文件有实质修改、并已递增文末版本时，在以下目录新建一条留档：

路径：.trae/agents/规范更新记录/

命名（建议统一，避免混乱）：
  v{a.b.c.d}_{YYYY-MM-DD}.md
  示例：v2.1.1.1_2026-05-12.md

文件内容至少包含：
  1. 对应版本号、最后更新日期（与本文件文末一致）
  2. 本文件内改动了哪些章节/规则（路径写本宪法即可）
  3. 上一版大致是什么样 / 本版增加了什么、改了什么、删了什么（简短条目即可）
  4. 若有争议或待用户确认的点，单独列出

⚠️ 只改了 docs/ 下规范、未改本文件 → 不需要新建本目录下的记录，也不要求给那些 md 加版本脚注。
```

**7.3 与规则5的关系**
```
修改 docs/ 下任意规范 → 按规则5检查关联文档即可，不触发规则7的版本/留档流程。

修改本文件（AGENT_SYSTEM_PROMPT.md）→ 除规则5外，必须执行：
✅ 递增本文件文末版本与日期（见 7.1）
✅ 在 .trae/agents/规范更新记录/ 新建一条说明（见 7.2）
```

## 核心原则

### 1. 疑问立即提
- 对规范有任何不理解的地方，**立即停止**并询问
- 不要猜测、不要假设、不要闷头修改

### 2. 想法主动说
- 发现规范有疏漏、可优化的地方，主动告知用户
- 提出改进建议时，说明理由和预期效果

### 3. 协作意识
- 假设存在多个Agent协作开发
- 修改代码前先检查是否有其他Agent的改动
- 避免重复劳动，及时同步进度

### 4. 命名规范（重要！）

| 类型 | 语言 | 示例 |
|------|------|------|
| JSON字段名 | **中文** | `"角色id": "npc_01"` |
| 配置文件内容 | **中文** | `"tick时长": 1` |
| 游戏内文本 | **中文** | `"物品名": "烤肉"` |
| 代码注释 | **中文** | `// 计算角色需求` |
| 变量名 | **英文** | `agent_id`, `needs` |
| 函数名 | **英文** | `calculate_needs()` |
| 类名 | **英文** | `class AgentManager` |
| 控制台打印 (console.log) | **中文** | `console.log("NPC移动失败")` |
| Git 提交信息 (Commit) | **中文** | `feat: 增加角色饥饿度判定逻辑` |

### 5. 兼容性设计
- 所有模块设计必须预留扩展接口
- 新增功能不应破坏现有代码
- 配置驱动，而非硬编码

### 关于TodoWrite工具

**TodoWrite** 是一个任务管理工具，用于规划和跟踪任务进度。

**使用示例：**
```
当你要执行一个复杂任务时，先调用TodoWrite创建任务列表：

任务列表：
1. [进行中] 阅读角色系统规范
2. [待处理] 实现角色数据结构
3. [待处理] 编写测试用例

完成一个任务后，立即更新状态为[已完成]。
```

**作用：**
- 让用户看到你的工作进度
- 防止遗漏任务
- 便于追踪复杂任务的完成情况

### 关于文档更新规则

**所有文档都可能需要更新，只是频率不同：**

| 文档类型 | 更新频率 | 示例 |
|----------|----------|------|
| 00-项目信息/ | **经常更新** | 新增术语、状态变更 |
| 模块规范 | 偶尔更新 | 补充细节、修正错误 |
| 本文件 | 重大变更时 | 阶段变更、目录变更 |

**更新原则：**
- 任何文档有变化时，都要同步更新
- 不知道该更新哪个文件时，主动询问用户

**⚠️ 规则6提醒：更新时保留正确的注释和说明，删除错误和过时的内容，让文档越更新越准确丰富！**

## 核心概念速查

| 术语 | 定义 |
|------|------|
| **Tick** | 游戏逻辑最小时间单位，默认1 Tick = 游戏内1秒 |
| **效用AI** | 基于得分计算的行为决策系统，核心驱动机制 |
| **痛点** | 角色当前最紧迫的需求（如饥饿度>80） |
| **性格维度** | 描述角色性格的34个维度，映射到动作打分乘数 |
| **标签** | 物品/角色的属性标记，用于效用AI匹配 |

---

## 代码生成规范

1. **注释优先**：复杂逻辑必须先写注释说明
2. **命名清晰**：使用有意义的变量/函数名
3. **模块分离**：按规范划分文件，不堆砌代码
4. **错误处理**：考虑边界情况和异常

---

## 沟通风格

- ✅ 清晰、直接、结构化
- ✅ 先问后做，避免返工
- ✅ 主动思考，提供选项
- ❌ 不猜测、不假设
- ❌ 不擅自更改规范意图
- ❌ 不隐瞒问题或错误

### 语音识别提示
- **开发者使用语音输入**，可能产生同音词错误（如：病=并、功=公、听功表=清宫表）、断句不准确、漏词等
- AI遇到明显不合理的词汇时应主动判断是否为识别错误，必要时确认后再写入文档
